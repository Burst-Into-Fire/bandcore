# Database

PostgreSQL **17** (image `postgres:17-alpine`, the same in docker-compose, the integration tests and production). Only standard PostgreSQL features are used, so the database can move between managed platforms and a VPS (RNF24). The major version is provisional until the hosting spike ([M1-10](roadmap/M01-project-foundation.md)) confirms what the platform offers.

## Roles

Row-level security only protects data if the role the API uses neither owns the tables nor can bypass RLS ([ADR-0002](adr/0002-multi-tenancy-shared-schema-band-id-rls.md)). There are two roles:

| Role | Used by | Can |
|---|---|---|
| `bandcore_owner` | Flyway, at API startup | Owns the `bandcore` schema and every object in it; runs DDL |
| `bandcore_app` | The API at runtime (datasource) | `SELECT`, `INSERT`, `UPDATE`, `DELETE` on tables; nothing else. `NOSUPERUSER`, `NOBYPASSRLS`, owns nothing, cannot create objects |

- Privileges for `bandcore_app` come from `ALTER DEFAULT PRIVILEGES` in the baseline migration, so every new table is usable automatically.
- Append-only tables (audit log, stock movements) must `REVOKE UPDATE, DELETE ... FROM bandcore_app` in their migration.
- Never use the owner or a superuser for the runtime connection, not even in tests.
- `DatabaseRolesIT` proves all of the above on every build.

## Bootstrap

The roles and the schema are created once per database by [`api/db/bootstrap/create-roles.psql`](../api/db/bootstrap/create-roles.psql). The script is idempotent: it only creates what is missing and resets the role attributes and passwords.

**Locally (docker-compose)** it runs automatically on the first start of the `db` container, with the passwords from `.env`. To run it again from scratch: `docker compose down -v`.

**Managed database (staging, production)**, once, as the administrator user the platform gives you:

```bash
psql "$ADMIN_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -v db_name=bandcore \
  -v owner_password="$DB_OWNER_PASSWORD" \
  -v app_password="$DB_APP_PASSWORD" \
  -f api/db/bootstrap/create-roles.psql
```

Then configure the API with `DB_OWNER_USER=bandcore_owner`, `DB_OWNER_PASSWORD`, `DB_APP_USER=bandcore_app` and `DB_APP_PASSWORD`. Generate both passwords randomly (for example `openssl rand -base64 32`) and keep them only in the platform's secret settings.

> [!NOTE]
> Some managed platforms do not give you a superuser. The administrator then needs `CREATEROLE`, and on PostgreSQL 16+ it may need `GRANT bandcore_owner TO <admin>` before `CREATE SCHEMA ... AUTHORIZATION bandcore_owner`. The spike M1-10 records the exact procedure for the chosen platform.

## Migrations

Flyway migrations live in [`api/src/main/resources/db/migration`](../api/src/main/resources/db/migration) and run automatically when the API starts, as `bandcore_owner`.

- **Naming:** `V{n}__{description}.sql`, with `n` the next integer and a short snake_case description, for example `V2__create_bands.sql`.
- **Never edit an applied migration.** Write a new one. Locally you can reset with `docker compose down -v`.
- **Breaking changes use expand and contract:** add the new column or table, deploy code that writes both, backfill, switch reads, and only then drop the old structure in a later release.
- Only standard SQL and PostgreSQL features; no platform extensions.
- Timestamps are `timestamptz` and stored in UTC (the database, the session and the JVM all use UTC). Calendar days and month boundaries are computed in the band's time zone.
- Money is `BIGINT` cents ([ADR-0006](adr/0006-money-as-integer-cents.md)). Identifiers are `uuid`, generated by the application ([ADR-0007](adr/0007-uuidv7-identifiers.md)).

### Tenant table checklist

Every table that holds band data must have, in the same migration:

- [ ] `band_id uuid NOT NULL` referencing `bands`
- [ ] `UNIQUE (band_id, id)`, so child tables can reference it with a composite key
- [ ] `ALTER TABLE ... ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`
- [ ] A policy comparing `band_id` with `app.band_id` for every command (`USING` and `WITH CHECK`)
- [ ] Composite foreign keys `(band_id, parent_id)` referencing `(band_id, id)` on the parent, so a row cannot point to another band's data
- [ ] An index (or unique constraint) whose first column is `band_id`
- [ ] For append-only tables: `REVOKE UPDATE, DELETE ON ... FROM bandcore_app`

The schema guard test (`SchemaGuardIT`) fails the build when a table misses any of these. Global tables (no `band_id`) must be added to its allowlist with a reason.

Template:

```sql
CREATE TABLE expenses (
    id          uuid        PRIMARY KEY,
    band_id     uuid        NOT NULL REFERENCES bands (id),
    member_id   uuid        NOT NULL,
    -- ...
    CONSTRAINT expenses_band_id_key UNIQUE (band_id, id),
    CONSTRAINT expenses_member_fk FOREIGN KEY (band_id, member_id) REFERENCES members (band_id, id)
);

ALTER TABLE expenses ENABLE ROW LEVEL SECURITY;
ALTER TABLE expenses FORCE ROW LEVEL SECURITY;

CREATE POLICY expenses_band_isolation ON expenses
    USING (band_id = NULLIF(current_setting('app.band_id', true), '')::uuid)
    WITH CHECK (band_id = NULLIF(current_setting('app.band_id', true), '')::uuid);
```

`NULLIF(..., '')` makes an unset context compare with `NULL`, so the policy returns no rows and rejects every write instead of failing with a cast error.

## Row-level security at runtime

The API sets two settings at the start of **every** transaction (`TenantAwareTransactionManager`), always with `set_config(name, value, true)`, which is local to the transaction:

| Setting | Value | Source |
|---|---|---|
| `app.band_id` | The band of the request | The host, resolved by `TenantResolutionFilter` (`TenantContextHolder`), never the request body, query or a header |
| `app.user_id` | The authenticated user | The validated access token |

Rules:

- **Tenant data is only accessed inside transactions.** Outside one, no band is set and tenant tables look empty. Services are `@Transactional`; repositories of tenant tables extend `TenantRepository`, which has no `findById` or `findAll`, and every query names the band (`findByBandIdAndId`).
- **Background jobs** that process several bands run one transaction per band, inside `TenantContextHolder.callAs(new TenantContext(bandId, slug), ...)`. There is no role that bypasses RLS.
- **Creating a band** is the only flow that changes the band inside a transaction (`RowLevelSecurity.switchBand`), to write the band's first rows atomically.
- `memberships` also lets a user read their own rows in every band (`app.user_id`), for the central "my bands" page. Writes always need the band.

`RowLevelSecurityIT` and `RowLevelSecurityPoolIT` prove the behavior, including a pool of one connection shared by transactions of different bands.
