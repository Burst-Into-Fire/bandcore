# M1 · Project Foundation

**Goal:** Set up the repository, backend and frontend skeletons, least-privilege database roles, integration test infrastructure, Docker, CI and the hosting spike, so every later issue lands on a consistent, tested base.

**Exit criteria:** `docker compose up --build` runs the whole stack locally; `./mvnw verify` runs unit and Testcontainers integration tests; CI runs on every pull request and blocks merges on failure; the hosting platform is chosen and wildcard subdomains are validated.

**Depends on milestones:** none

## M1-03 · Bootstrap Spring Boot API skeleton

**Labels:** type:chore, area:backend, priority:high
**Depends on:** M1-01

### Context

The API needs a structure that keeps modules independent from the start, so new modules (press, Instagram, billing) can be added later without tangling the code.

### Scope

- [ ] Java 25, latest stable Spring Boot 4.x, Maven wrapper
- [ ] Spring Modulith with top-level modules `identity`, `tenancy`, `finance`, `merch`, `audit` and `shared`, each with `package-info.java` and internal subpackages
- [ ] All API routes under `/api`
- [ ] Actuator on a separate management port (not routed by the public proxy), exposing liveness and readiness only
- [ ] springdoc-openapi (`/api/v3/api-docs`); Swagger UI enabled only outside production
- [ ] Global error handling with RFC 9457 Problem Details: consistent validation error format, stable error codes, no stack traces or SQL in responses
- [ ] Configuration only through environment variables; dev-only defaults; the production profile fails fast when a secret is missing
- [ ] Structured JSON logging with a request id (`X-Request-Id` generated or propagated, stored in MDC and returned in the response)
- [ ] Inject `java.time.Clock` everywhere time is read, so tests can fix it

### Acceptance criteria

- `./mvnw verify` passes
- Health endpoints respond on the management port only
- An unknown route returns `application/problem+json`

### Tests required

- Integration: context loads; 400, 404 and 500 responses are Problem Details without internal details; the request id is echoed in the response header and present in logs
- Architecture: `ApplicationModules.of(...).verify()` passes

## M1-04 · Set up PostgreSQL, Flyway and least-privilege database roles

**Labels:** type:chore, area:database, priority:critical
**Depends on:** M1-03

### Context

Row-Level Security only protects data if the application role neither owns the tables nor can bypass RLS. This has to be true from the first migration.

### Scope

- [ ] Pin the PostgreSQL major version (aligned with the managed version chosen in M1-10)
- [ ] Roles: `bandhub_owner` owns the schema and runs Flyway; `bandhub_app` is the runtime role with `NOSUPERUSER`, `NOBYPASSRLS` and no object ownership
- [ ] Grants through `ALTER DEFAULT PRIVILEGES` so new tables are automatically granted to `bandhub_app` (append-only tables revoke `UPDATE`/`DELETE` explicitly)
- [ ] Separate credentials: Flyway uses the owner, the datasource uses the app role
- [ ] Baseline migration; only standard PostgreSQL features (no platform-specific extensions)
- [ ] Role bootstrap SQL for docker-compose and a documented procedure for the managed database
- [ ] Migration conventions in `docs/`: naming (`V{n}__{description}.sql`), never edit applied migrations, expand/contract for breaking changes, and the tenant table checklist (`band_id NOT NULL`, RLS, policies, composite foreign keys, index starting with `band_id`)
- [ ] Timestamps stored as `timestamptz` in UTC

### Acceptance criteria

- The API starts connected as `bandhub_app` and cannot run DDL
- Flyway migrates using the owner role
- `bandhub_app` has `rolbypassrls = false` and owns no objects

### Tests required

- Integration (Testcontainers): `CREATE TABLE` as `bandhub_app` fails; `pg_roles` shows no bypass and no superuser for the app role; the app role owns no tables

### Security notes

- Never use the owner or a superuser for the runtime connection, including in tests

## M1-05 · Set up backend integration test infrastructure with Testcontainers

**Labels:** type:test, area:backend, priority:critical
**Depends on:** M1-04

### Context

Integration tests are the primary test layer. They must run against the same PostgreSQL as production, connected with the same role, so RLS and constraints are exercised for real.

### Scope

- [ ] Testcontainers PostgreSQL with the same image and tag as production, one container shared by all test classes (reuse enabled locally)
- [ ] Flyway runs as the owner and the application connects as `bandhub_app` in tests
- [ ] Surefire runs unit tests (`*Test`), Failsafe runs integration tests (`*IT`); `./mvnw verify` runs both
- [ ] Base support for integration tests: HTTP test client helpers, request helpers that set the `Host` header per band, a fixed `Clock`, and a cleanup strategy (truncate as owner, or a fresh tenant per test)
- [ ] Test data builders (`aBand()`, `aUser()`, …) that each module extends
- [ ] JaCoCo report combining unit and integration tests
- [ ] jqwik for property-based tests
- [ ] ArchUnit baseline rules: no `float` or `double` in domain packages, no field injection, controllers do not use repositories directly
- [ ] Spring Modulith `verify()` test and generated module documentation

### Acceptance criteria

- A sample integration test runs against real PostgreSQL locally (with only Docker installed) and in CI
- The baseline suite run time is recorded in the PR to track regressions

### Tests required

- A smoke integration test proving the app connects as `bandhub_app` and Flyway ran as the owner

## M1-07 · Dockerize services and set up local docker-compose

**Labels:** type:chore, area:infra, priority:high
**Depends on:** M1-03, M1-04, M1-06

### Context

The same images run locally and in every environment. The web container proxies `/api` so the API is always same-origin, which is a core part of the tenant isolation design.

### Scope

- [ ] Backend Dockerfile: multi-stage (Maven build, slim JRE runtime), non-root user, container-aware JVM flags, healthcheck
- [ ] Frontend Dockerfile: build stage plus unprivileged nginx serving the SPA with history fallback and reverse proxy of `/api` to the API; the management port is not proxied
- [ ] nginx baseline: no server tokens, long cache for hashed assets, no cache for `index.html`
- [ ] `docker-compose.yml` with `db` (running the role bootstrap scripts), `api`, `web` and `mailpit`; healthchecks and `depends_on` with `service_healthy`
- [ ] `.env.example` with every variable (`BASE_DOMAIN`, owner and app database credentials, `JWT_SECRET`, SMTP settings, …); README variable table updated
- [ ] Local subdomains via `*.localhost` (for example `http://app.localhost:3000` and `http://burst.localhost:3000`), documented for WSL and Windows browsers

### Acceptance criteria

- `cp .env.example .env && docker compose up --build` brings every service up healthy
- `http://app.localhost:3000` serves the SPA and `/api` reaches the API through nginx

### Tests required

- Compose smoke test (used by CI in M1-08): start the stack and call the API health through the proxy

## M1-08 · Set up GitHub Actions CI for build and tests

**Labels:** type:chore, area:infra, priority:critical
**Depends on:** M1-05, M1-06, M1-07

### Context

Every pull request must prove it keeps the rules intact. Tests that do not block merges are not a safety net.

### Acceptance criteria

- A pull request with a failing test cannot be merged
- Baseline CI duration is under 15 minutes

### Tests required

- Verified by opening a pull request with a deliberately failing test (and reverting it)

## M1-10 · Spike: choose hosting platform and validate wildcard subdomains

**Labels:** type:spike, area:infra, priority:high
**Depends on:** M1-07

### Context

One subdomain per band only works if the hosting platform supports wildcard custom domains with TLS and private networking between the web and API containers. This must be validated before the authentication design is built in M2.

### Scope

- [ ] Compare Railway and Render on: wildcard custom domains with automatic TLS, private networking (web → API without exposing the API publicly), managed PostgreSQL versions, ability to create extra roles without superuser, access to `pg_dump` for off-platform backups, preview environments, region and latency to Brazil, cost for staging and production
- [ ] Deploy the compose-equivalent stack (web, API, database) to the preferred platform with a wildcard domain
- [ ] Verify which `Host` and `X-Forwarded-*` headers reach the API through the platform proxy
- [ ] Record the decision as ADR-0011 and set the PostgreSQL major version used by M1-04 and M1-05

### Acceptance criteria

- Two different subdomains reach the same deployment over HTTPS and the API sees the correct `Host`
- ADR-0011 is merged

### Tests required

- Manual verification documented in the ADR (commands and results)
