# M8 · Sales, Refunds & Events

**Goal:** Complete the online part of the merch module: events (shows), atomic sales, refunds that restore stock, event closing with profit per product, the quick sale screen and the merch part of the dashboard.

**Exit criteria:** a member can sell at a show from the phone in a few taps; refunds restore stock; an admin closes the event and sees revenue, COGS and profit per product; the dashboard shows merch sales, profit and stock as in the mockup.

**Depends on milestones:** M7

---

**Labels:** type:feature, area:backend, module:merch, priority:high
**Depends on:** M7-01

### Context

Sales usually happen at shows, and the closing report is per show.

### Scope

- [ ] `events` tenant table: name, venue, city, `starts_at`, `status` (`OPEN`, `CLOSED`), `closed_at`, `closed_by`
- [ ] Admins and members create and edit; only admins close (M8-04)
- [ ] Lists of upcoming and past events

### Acceptance criteria

- Events can be created and listed, and sales can be linked to an open event

### Tests required

- Integration: CRUD and validation; authorization matrix and isolation entries

## M8-02 · Register sales atomically

**Labels:** type:feature, area:backend, module:merch, priority:critical, needs-discussion
**Depends on:** M7-02, M7-03, M8-01

### Context

A sale and its stock update happen in the same transaction. The sale also freezes the price and the unit cost at that moment, so later changes do not rewrite past profit.

### Open question

The requirements now include BRL and USD (RF40, RNF08, RN08), with totals and balances computed per currency. This issue was written for BRL only and needs a currency dimension once that is confirmed.

### Scope

- [ ] `sales` tenant table: `id` generated by the client (idempotency key), optional `event_id`, `sold_at`, seller, `payment_method` (`CASH`, `PIX`, `CARD`, `OTHER`; recorded only, no payment integration), `total_cents`, `status` (`COMPLETED`, `PENDING_RECONCILIATION`, `CANCELLED`), `source` (`ONLINE`, `OFFLINE`)
- [ ] `sale_items`: variant, quantity, `unit_price_cents` snapshot, `unit_cost_cents` snapshot (current average cost), optional discount with reason
- [ ] One transaction: insert sale and items, decrement stock through `StockService` (`SALE` movements)
- [ ] Insufficient stock → 409 with availability per item
- [ ] Idempotent `POST`: the same id with the same payload returns the existing sale; the same id with a different payload → 409
- [ ] Selling on a closed event → 409

### Acceptance criteria

- No sale is ever recorded without its stock movement, or the other way around

### Tests required

- Integration: a sale decrements stock and stores both snapshots; a multi-item sale with one item short is rejected entirely and stock is unchanged; a retried request returns the same sale without decrementing again; concurrent sales of the last unit over HTTP; closed event → 409; a variant from another band → rejected; authorization matrix and isolation entries; audit events

## M8-03 · Process refunds that restore stock

**Labels:** type:feature, area:backend, module:merch, priority:critical
**Depends on:** M8-02

### Context

Refunds give money back and usually put the item back into stock. They can never exceed what was sold.

### Scope

- [ ] `refunds` and `refund_items` tenant tables: sale item, quantity, `amount_cents`, reason
- [ ] Partial and full refunds; refunded quantity per item never exceeds sold minus already refunded (enforced under a row lock or conditional update)
- [ ] Restock per item (default yes, creating a `REFUND` movement); no movement when the item is not restocked
- [ ] Refund amount defaults to unit price × quantity
- [ ] Permissions per the matrix (admins always; members on open events)
- [ ] Audited

### Acceptance criteria

- Refunds restore stock and reduce net revenue, and an item cannot be refunded twice

### Tests required

- Integration: a partial refund restores stock and lowers net revenue; refunding more than sold → 409; two concurrent refunds of the same item → only one succeeds; refunding a cancelled or pending sale → 409; isolation entry; audit events

## M8-04 · Close events and generate profit report

**Labels:** type:feature, area:backend, module:merch, priority:high, needs-discussion
**Depends on:** M8-03

### Context

After a show, the band needs to know what sold, how much came in by payment method (to check the cash box and PIX), and the profit per product.

### Open question

RF21 has a unit cost entered manually on each product. This roadmap derives the unit cost from production batches (weighted average). To be decided before this issue starts.

### Scope

- [ ] Report per event, by product and variant: units sold, gross revenue, refunds, net revenue, COGS (quantity × the unit cost snapshot, net of restocked refunds), gross profit and margin
- [ ] Totals by payment method
- [ ] Pending reconciliation sales listed separately (M9-05)
- [ ] Closing (admins): sets `CLOSED` and stores an immutable snapshot of the report; later changes (late refunds) are shown as post-closing adjustments
- [ ] Reopening only by admins, audited

### Acceptance criteria

- The closing report shows revenue, COGS and profit per product, calculated from the snapshots

### Tests required

- Unit: report calculator including refunds
- Integration: an event with sales and refunds produces the expected numbers (COGS uses snapshots, not the current average cost); closing stores the snapshot; sales after closing → 409; authorization matrix and isolation entries

## M8-05 · Provide merch summary metrics

**Labels:** type:feature, area:backend, module:merch, priority:high, needs-discussion
**Depends on:** M8-04

### Context

The dashboard shows merch sales, items sold, profit after production cost and low stock for the month.

### Open question

The requirements now include BRL and USD (RF40, RNF08, RN08), with totals and balances computed per currency. This issue was written for BRL only and needs a currency dimension once that is confirmed.

### Scope

- [ ] `GET /api/summary/merch?month=YYYY-MM`: net revenue, items sold, profit after COGS, low-stock variants and top products
- [ ] Month boundaries in the band timezone

### Acceptance criteria

- The summary returns correct numbers for a month with sales, refunds and several batches

### Tests required

- Integration: data like the mockup (58 items, R$ 2.340,00 revenue) with profit computed as revenue − COGS. The mockup's R$ 1.140,00 subtracts the whole batch cost; the test documents the difference; timezone boundaries; isolation entry

## M8-06 · Build quick sale screen

**Labels:** type:feature, area:frontend, module:merch, priority:critical
**Depends on:** M4-06, M8-02

### Context

At the merch table there is no time for forms. A single-item sale should take only a few taps on a phone.

### Scope

- [ ] Mobile-first screen one tap away from the navigation
- [ ] Active event selector (remembered)
- [ ] Grid of variants with large touch targets (product and size) showing stock; tap to add, quantity stepper
- [ ] Payment method chips (*Dinheiro*, *PIX*, *Cartão*), total, confirm; success feedback and reset for the next sale
- [ ] Client-generated UUID per sale, reused on retries (prepares M9)
- [ ] Clear handling of 409 insufficient stock
- [ ] Usable at 360 px

### Acceptance criteria

- A single-item sale takes at most four taps

### Tests required

- Vitest: cart logic in cents; the same UUID is reused on retry
- E2E: a sale on a 360 px viewport updates stock
